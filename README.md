# local-doc-rag

Офлайн-поиск по инженерной документации: BM25 и векторный поиск, слитые через RRF, плюс ответ локальной языковой модели со ссылками на фрагменты. Работает без интернета, когда модели уже скачаны. Есть HTTP API на FastAPI и командная строка.

Все документы в репозитории синтетические. Стенды «ИС-7», «ГС-4», контроллеры серии «К-200», модули «МВА-8», номера протоколов и уставки выдуманы и сгенерированы скриптом `data/synthetic/make_synthetic.py`. Реальных документов, названий предприятий и данных заказчиков здесь нет.

## Что умеет и чего не умеет

| Умеет | Не умеет |
|---|---|
| Читать `.md`, `.txt`, `.pdf` с текстовым слоем (pypdf) | Сканы без текстового слоя: такой PDF пропускается с предупреждением, OCR нет |
| Резать текст на фрагменты по 800 символов с перекрытием 150, не разрывая строки и перенося шапку markdown-таблицы | `.docx`, `.xlsx`, чертежи, таблицы из PDF как таблицы |
| Искать тремя способами: `bm25`, `vector`, `hybrid` (RRF, k = 60) | Дописывать индекс: при каждом `ingest` он пересобирается целиком |
| Отвечать через llama.cpp (GGUF) или Ollama, со ссылками `[n]` | Гарантировать «Не знаю», когда ответа нет: модель 3B не отказалась на 2 ловушках из 10, а с промптом v2 на вопрос про IP-адрес панели оператора (его в документах нет) назвала адрес контроллера. Замер ниже |
| Работать без LLM (`--no-llm`): отдать цитаты или «Не знаю» по порогу | Авторизацию, разграничение доступа, многопользовательский режим |
| Кешировать эмбеддинги на диске (повторная индексация того же корпуса — 2,2 с; с нуля — от 32,6 до 36,1 с в пяти запусках) | Веб-интерфейс: есть только Swagger UI на `/docs` |

## Запуск за 5 команд

Python 3.11 или новее. Отдельное виртуальное окружение желательно (`python -m venv .venv`), но в счёт команд не входит.

```
git clone https://github.com/gdm0991/local-doc-rag
cd local-doc-rag
pip install -r requirements.txt
python -m local_doc_rag ingest data/synthetic/docs
python -m local_doc_rag serve --no-llm
```

После этого Swagger UI доступен на http://127.0.0.1:8000/docs. Можно обойтись без сервера:

```
python -m local_doc_rag ask "Какая аварийная уставка давления масла на стенде ИС-7?" --no-llm
```

При первом `ingest` fastembed скачивает модель `intfloat/multilingual-e5-small`, 465 МБ на диске (`du -shL` по кешу Hugging Face). Модель ложится в `~/.cache/local-doc-rag/models`, путь меняется переменной `LDR_MODEL_CACHE`. Если скачать не удалось или fastembed не установлен, включается запасной TF-IDF, см. «Ограничения».

На Windows те же цели есть в `make.ps1`: `.\make.ps1 install`, `.\make.ps1 ingest`, `.\make.ps1 test`. На Windows я эти команды не запускал: репозиторий собирался и проверялся на Linux.

### С локальной моделью

```
pip install llama-cpp-python --extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cpu
hf download Qwen/Qwen2.5-3B-Instruct-GGUF qwen2.5-3b-instruct-q4_k_m.gguf --local-dir models
python -m local_doc_rag ask "Какая аварийная уставка давления масла на стенде ИС-7?" --model models/qwen2.5-3b-instruct-q4_k_m.gguf
```

Файл модели весит 2,1 ГБ (`ls -l`). Сам я скачивал его не командой `hf`, а функцией `hf_hub_download` из того же пакета `huggingface_hub`. На Linux из указанного индекса ставится готовое колесо `llama-cpp-python` без компиляции. Есть ли там колесо под вашу версию Python на Windows, я не проверял.

Ollama: `--llm ollama --model qwen2.5:3b`, адрес задаётся `LDR_OLLAMA_URL`. Клиент Ollama написан, но ни разу не запускался: в среде сборки Ollama не было.

## Как устроено

```
 .md  .txt  .pdf
       │  ingest.py — pypdf для PDF; пустой или битый файл пропускается
       ▼
 chunking.py — 800 символов, перекрытие 150, режет по строкам;
       │       к фрагменту из середины таблицы приписывается её шапка
       │       к тексту для индекса приписывается заголовок документа
       ├────────────────────────────┬─────────────────────────────────┐
       ▼                            ▼                                 │
 index_bm25.py                index_vec.py                            │
 rank_bm25 + стеммер Snowball  fastembed (ONNX), e5-small, 384 изм.   │
 «ИС-7», «0,25» — один токен   кеш векторов: index/vectors_<hash>.npy │
       │ топ-50                     │ топ-50                          │
       └──────────┬─────────────────┘                                 │
                  ▼                                                   │
        hybrid.py — RRF: score = Σ 1/(60 + место)                     │
                  │ топ-5 фрагментов                                  │
        ┌─────────┴────────────────┐                                  │
        ▼                          ▼                                  │
  --no-llm: цитаты            llm.py: llama.cpp или Ollama            │
  или «Не знаю», если         ответ со ссылками [n] или «Не знаю»     │
  покрытие запроса < 0,424                                            │
        └─────────┬────────────────┘                                  │
                  ▼                                                   │
        api.py (FastAPI): POST /ingest /search /ask, GET /health ◄────┘
        cli.py (typer):   ldr ingest | search | ask | serve
```

RRF выбран потому, что смотрит только на места в выдаче. Оценки BM25 (десятки) и косинусы (от 0 до 1) не приходится приводить к одной шкале.

`GET /health` показывает, какой векторный бэкенд реально работает (`embed_backend`) и почему включился запасной, если включился (`embed_fallback_reason`). `POST /ingest` принимает только пути внутри `LDR_INGEST_ROOT` (по умолчанию текущая папка), остальные получают 403.

## Метрики: 28 из 30 по поиску, 18 из 30 по ответам

Корпус: 93 документа (77 `.md`, 8 `.txt`, 8 `.pdf`), 155 фрагментов. Вопросы: 30 с проверяемым ответом и 10 ловушек, ответа на которые в корпусе нет (`eval/questions.jsonl`). Эталонные ответы и документы-источники берутся из реестра фактов генератора (`data/synthetic/facts.json`), формулировки вопросов написаны вручную и намеренно не повторяют текст документов.

Замер 1 октября 2026 года на облачной виртуальной машине, где собирался репозиторий: Intel Xeon 2,1 ГГц, 2 логических ядра, 7,8 ГБ ОЗУ, **без GPU**, Python 3.11.15. На своих машинах я не замерял. Каждая цифра — один прогон, а не среднее. Полные таблицы по каждому вопросу: `eval/results_2026-10-01.md`.

**Поиск** (`pipeline.search`, первые 10 фрагментов):

| Режим | Recall@5 | MRR@10 | p50 / p95 поиска, мс |
|---|---|---|---|
| hybrid | 0,93 (28 из 30) | 0,84 | 10,3 / 13,6 |
| bm25 | 0,93 (28 из 30) | 0,78 | 0,4 / 0,7 |
| vector | 0,90 (27 из 30) | 0,82 | 11,2 / 15,6 |

- Recall@5 — доля вопросов, у которых хотя бы один из первых 5 фрагментов взят из документа-источника.
- MRR@10 — среднее 1/место первого такого фрагмента, 0, если его нет в первой десятке.
- Время — `time.perf_counter` вокруг вызова в процессе, без HTTP; кеш эмбеддинга запроса очищается перед каждым замером; p95 считается методом ближайшего ранга по 30 замерам.

Гибрид не нашёл больше документов, чем BM25: те же 28 из 30. Разница видна только в MRR, то есть нужный фрагмент стоит выше. Мимо первой пятёрки прошли Q11 (температура обмотки статора ЭС-1, источник на 7-м месте) и Q12 (расходомер масла ИС-9, 9-е место). Оба вопроса про строку в таблице перечня сигналов.

Во втором прогоне на той же машине p50 гибридного поиска получилось 20,9 мс вместо 10,3. Код поиска между прогонами не менялся. Почему время удвоилось, я не знаю.

**Отказ «Не знаю» без LLM.** Правило: если доля IDF-веса терминов запроса, найденных в первом фрагменте, ниже 0,424, система отказывается. Порог подобран на отдельных 10 вопросах (`eval/calibration.jsonl`, с основным набором не пересекаются), там верно 8 из 10.

| | Результат |
|---|---|
| «Не знаю» на ловушках | 6 из 10 |
| Ложные «Не знаю» на вопросах с ответом | 10 из 30 |

Эвристика слабая. Она ловит несуществующий стенд «ИС-11», но пропускает «уставку по виброскорости на ИС-3»: все слова вопроса в корпусе есть, только про другие стенды.

**Ответы модели.** Qwen2.5-3B-Instruct Q4_K_M через llama-cpp-python 0.3.36, temperature 0, в контексте 5 фрагментов гибридного поиска.

| | Промпт v1 (по умолчанию) | Промпт v2 (`LDR_PROMPT=v2`) |
|---|---|---|
| Верный ответ (все ключевые значения есть, отказа нет) | 18 из 30 | 16 из 30 |
| «Не знаю» на ловушках | 8 из 10 | 9 из 10 |
| Ложные «Не знаю» | 3 из 30 | 4 из 30 |
| p50 / p95 полного ответа, по 40 вопросам | 81,5 / 103,0 с | 78,1 / 92,5 с |

Отчёты: `eval/results_2026-10-01.md` (v1) и `eval/results_2026-10-01_run2_prompt-v2.md` (v2). Промпт v2 я написал после того, как увидел ответы v1: в 7 ответах из 30 модель выдала только номер фрагмента, например «[1]», без значения. v2 эту проблему не решил: в 5 ответах вместо «[1]» модель написала просто «1». Верных ответов при этом стало на два меньше. Два вопроса из тридцати — в пределах шума, поэтому лучше ни один промпт не назову. По умолчанию оставлен v1: у него больше верных ответов. Для v2 набор вопросов уже не «слепой», это стоит учитывать.

Полторы минуты на ответ получены на двух ядрах без GPU, с GPU я не замерял. Сколько из этого времени уходит на чтение промпта, а сколько на генерацию, тоже не знаю: отдельно не мерил.

Перед 3B я попробовал Qwen2.5-1.5B Q4_K_M на двух вопросах вручную. На вопрос с ответом модель выдала «[1]», на ловушке выдумала уставку. Это два наблюдения, а не замер, и в таблицы они не вошли.

## Как воспроизвести

```
python data/synthetic/make_synthetic.py   # корпус и facts.json (seed 20261001)
python eval/make_questions.py             # questions.jsonl и calibration.jsonl
python eval/run_eval.py                   # поиск и отказ без LLM, около 1 минуты
python eval/run_eval.py --llm llamacpp --model models/qwen2.5-3b-instruct-q4_k_m.gguf   # около 1 часа на 2 ядрах
python -m pytest -q                       # 34 теста, без сети и без LLM
```

Тесты используют TF-IDF вместо e5 (`LDR_EMBED_BACKEND=tfidf` в `tests/conftest.py`), чтобы CI не скачивал 465 МБ модели. CI (`.github/workflows/ci.yml`) гоняет pytest на Ubuntu и Windows с Python 3.11 и 3.12 и проверяет, что генератор воспроизводит закоммиченный корпус. До публикации репозитория CI ни разу не запускался.

## Ограничения и что нашлось при сборке

- **Синтетика однородная.** Восемь стендов, у каждого 11 документов одинаковой структуры. На живом архиве, где один и тот же параметр в разных документах называется по-разному, Recall, скорее всего, ниже. Насколько ниже, не знаю.
- **Набор маленький.** Один вопрос — это 3,3 процентного пункта. Разница между режимами поиска (28 против 27) — один вопрос.
- **Проверка ответа идёт по подстроке.** Первая версия проверки засчитала ответ «[5]» на вопрос с эталоном «5 с», приняв номер фрагмента за значение. Исправлено: ссылки `[n]` вырезаются, числа сравниваются по границам, на это есть тест. До исправления точность v1 считалась как 19 из 30, после стала 18. Но и исправленная проверка ошибается в обе стороны. Ответ v2 «2 слот, 3 канал» верный, но не засчитан, потому что эталон записан как «слот 2, канал 3». А путаная фраза v1 на Q01 засчитана, потому что содержит верное число 0,24.
- **Стеммер.** Snowball режет «Прогрев» до «прогр», а «прогрева» до «прогрев», и BM25 эти формы не сопоставляет. Нашлось на тесте API.
- **BM25 на крошечном корпусе.** В `BM25Okapi` у слова, которое встречается в половине документов, IDF равен нулю. Первая версия отбрасывала такие совпадения, и на корпусе из двух документов выдача становилась пустой. Исправлено: кандидатом считается любой фрагмент, где есть хотя бы одно слово запроса.
- **e5-small в fastembed.** В fastembed 0.8.1 этой модели нет во встроенном списке, поэтому `index_vec.py` регистрирует ONNX-файл из репозитория модели через `add_custom_model`. Как это поведёт себя в других версиях fastembed, я не проверял.
- **Запасной TF-IDF не семантический.** Он считает общие куски символов (n-граммы от 2 до 4), а не смысл. В этом замере он не включался, все цифры выше получены с e5-small. Отдельно метрики на TF-IDF я не снимал.
- **Версионности документов нет.** Если в корпусе лежат две редакции одного документа, система не знает, какая из них действует.

## Чем отличается от продакшн-версии

С мая 2026 года я делаю офлайн-поиск по инженерной документации предприятия: локальные модели, гибридный поиск BM25 и векторный, слияние через RRF. Та система работает на закрытом архиве. Этот репозиторий — её открытая демонстрация, написанная заново.

| | Здесь | Продакшн-система |
|---|---|---|
| Данные | 93 синтетических документа, сгенерированных скриптом | закрытый архив предприятия; документы, индексы и логи запросов не публикуются |
| Код | написан с нуля для публикации, под MIT | не публикуется; код оттуда сюда не переносился |
| Метрики | измерены на синтетике, все выше | здесь не приводятся: их нельзя проверить без закрытых данных |
| Железо замера | облачная ВМ, 2 ядра, без GPU | здесь не описывается |

Метрики этого репозитория нельзя переносить на продакшн-систему, и наоборот.
